# Watchdog design for the single-core superloop (`pico-link-ufh`)

Author: Ada (architect), 2026-08-30. Design of record for `pico-link-ufh`.
Supersedes `pico-link-1rp` (per `pico-link-cz0.6`, which redecided the design
around the single-core superloop).

## Context — verified state of the code

- `main()` runs one thread-context superloop on core0, `main.c:326`. Body:
  X+Y BOOTSEL hatch, `pl_link_input_poll`, `pl_bt_drain_events`, `pl_ui_tick`,
  `pl_ui_render`, `st7789_blit_framebuffer`, `pl_bt_poll_commands`, the
  audio-rate report, `pl_usb_pump_report()` (`main.c:428`), `pl_a2dp_report()`
  (`main.c:434`), then a pacing sleep to a 16 000 us budget (`main.c:302`,
  `main.c:449-451`).
- **USB is not pumped by the superloop.** `pl_usb_pump_init()`
  (`usb_pump.c:107-117`) installs a 1 ms repeating timer that pends a claimed
  user IRQ at priority 0xC0; `pl_usb_pump_worker_irq()` (`usb_pump.c:40-77`) is
  where `tud_task()` (`usb_pump.c:57`) and `pl_usb_audio_task()` run. It early-
  returns without calling `tud_task()` when `pl_usb_mutex` is contended
  (`usb_pump.c:53-55`).
- **BTstack runs in the cyw43 background IRQ** at `PICO_LOWEST_IRQ_PRIORITY`
  (0xFF) — `pico_cyw43_arch_threadsafe_background`, `firmware/CMakeLists.txt:186`;
  documented at `bt.c:44-46` and `a2dp.c:20-23`.
- **The media pump is a BTstack run-loop timer**, `pl_a2dp_media_timer_handler`
  (`a2dp.c:552`), 10 ms period (`PL_A2DP_AUDIO_TIMEOUT_MS`), armed only from
  `STREAM_ESTABLISHED` (`a2dp.c:910`) and removed on `STREAM_RELEASED` /
  `SIGNALING_CONNECTION_RELEASED` (`a2dp.c:974-977`, `987-990`). It already keeps
  `s_ctx.tick_count` (`a2dp.c:191`, incremented `a2dp.c:634`).
- **No watchdog is armed anywhere.** `hardware_watchdog` is linked
  (`CMakeLists.txt:175`); the only non-panic call is `watchdog_reboot(0,0,...)` at
  `usb_reset.c:82` (RESET_REQUEST_FLASH). The panic recorder arms
  `watchdog_enable(500, false)` on every panic path (`panic_recorder.c:124, 188,
  235, 305`).
- **Scratch registers are fully allocated today:** `scratch[0..3]` = panic
  recorder payload (magic / address / diag / retry, `panic_recorder.c:131-150`);
  `scratch[4..7]` = pico-sdk's own arm/reboot handshake (`watchdog.c:82, 100-103`).
- SDK facts read, not assumed: `watchdog_update()` is a single store of
  `load_value` (`watchdog.c:26-28`); `_watchdog_enable` sets `PSM_WDSEL` to reset
  everything except ROSC/XOSC (`watchdog.c:48`) and clamps the load at
  `WATCHDOG_LOAD_BITS` (0xFFFFFF us ~= **16.777 s ceiling**, `watchdog.c:67`,
  `WATCHDOG_XFACTOR == 1` on RP2350); ticks are started for all generators by
  `runtime_init_clocks`'s `start_all_ticks` (`runtime_init_clocks.c:28-38`), so
  **no `watchdog_start_tick()` call is needed**; `watchdog_enable_caused_reboot()`
  = `reason != 0 && scratch[4] == 0x6ab73121` (`watchdog.c:123-125`).

## Decision

Two mechanisms, one feed site.

### 1. Software supervisor (`pl_wdt`) with per-subsystem progress counters

New module `firmware/src/watchdog_sup.{c,h}`:

```c
typedef enum {
    PL_WDT_USB_TIMER = 0,   // the 1ms timer -> 0xC0 IRQ path is still firing
    PL_WDT_USB_TASK,        // tud_task() is actually being reached
    PL_WDT_BTSTACK,         // the BTstack run loop is still servicing timers
    PL_WDT_MEDIA,           // the A2DP media timer is ticking (conditional)
    PL_WDT_COUNT
} pl_wdt_subsys_t;

void pl_wdt_kick(pl_wdt_subsys_t s);              // one volatile uint32 increment
void pl_wdt_set_enabled(pl_wdt_subsys_t s, bool); // enabling re-bases the deadline
void pl_wdt_arm(void);                            // watchdog_enable(PL_WDT_TIMEOUT_MS, true)
void pl_wdt_service(void);                        // THE feed site; once per superloop
void pl_wdt_blackout_begin(void);                 // for the cz0.6.1 flash write path
void pl_wdt_blackout_end(void);                   // re-bases every deadline to now
void pl_wdt_report(void);                         // 1Hz: per-subsystem max staleness
void pl_wdt_report_boot_reason(void);             // call BEFORE pl_wdt_arm()
```

`pl_wdt_service()` semantics: for each **enabled** subsystem, if its counter
changed, stamp `last_change_us = now`; else if `now - last_change_us >
deadline_us`, it is **stale**. No subsystem stale -> `watchdog_update()`. A
subsystem stale -> write the breadcrumb and `watchdog_reboot(0, 0, 10)`.

Counters, not 64-bit timestamps: a `uint32_t` volatile increment has exactly one
writer per slot and is read atomically by the supervisor on M33. A `time_us_64()`
stamp written from IRQ and read from thread context can tear.

**Subsystem table:**

| Subsystem | Evidence | Expected rate | Deadline | Tier |
|---|---|---|---|---|
| Superloop | *is* the feed site | ~20-60 Hz | (hardware timeout) | MUST |
| `PL_WDT_USB_TIMER` | kick at the **top** of `pl_usb_pump_worker_irq` (`usb_pump.c:41`, **before** the `mutex_try_enter` early-return at :53) | 1000 Hz | 100 ms | MUST |
| `PL_WDT_USB_TASK` | kick immediately after `tud_task()` returns (`usb_pump.c:57`) | 1000 Hz minus contention | 250 ms | MUST |
| `PL_WDT_BTSTACK` | a **new permanent 100 ms `btstack_run_loop` timer** registered in `pl_bt_init` (`bt.c:432`) that kicks and re-arms | 10 Hz | 1000 ms | MUST |
| `PL_WDT_MEDIA` | `s_ctx.tick_count` (`a2dp.c:634`) — kick at top of `pl_a2dp_media_timer_handler` (`a2dp.c:552`) | 100 Hz **while streaming** | 500 ms | MUST, **enabled only in `PL_A2DP_MEDIA_STREAMING`** |
| USB audio packets | `pl_usb_audio_packet_count()` | host-dependent | 500 ms | **REPORT ONLY — never resets** |

Why the USB pump splits into two counters: `USB_TIMER` proves the alarm/IRQ
plumbing is alive; `USB_TASK` proves the pump is doing its job. Sustained
`pl_log` mutex contention would satisfy the first and starve the second, and that
starvation is precisely what kills the ISO-OUT endpoint permanently
(`audio_device.c:759-762`, chain documented in `usb_pump.h:1-14`). One counter
would hide it.

Why the BTstack heartbeat is a *new* timer rather than reusing the media timer:
the media timer only exists while a stream is established (`a2dp.c:910`,
`974-977`). Without a dedicated heartbeat there is no evidence of the run loop at
all in the idle/scanning state — which is most of the device's life.

Why USB-audio packet flow is report-only: a host legitimately idling in
alt-setting 1 is indistinguishable, from here, from the dead endpoint. There is
no measured evidence of what macOS does at idle, and a false reboot mid-listening
is worse than a missed detection. Instrument it, watch the margin, promote it
later on data.

### 2. Hardware watchdog as the backstop for "the superloop stopped executing"

`PL_WDT_TIMEOUT_MS = 2000`, `pause_on_debug = true`.

#### Timeout arithmetic

The hardware load must exceed the longest *legitimate* gap between two
consecutive `pl_wdt_service()` calls:

| Term | ms | Source |
|---|---|---|
| Flash sector erase, IRQs off (cz0.6.1) | 400 | worst case |
| 16 x 256 B page programs @ 3 ms worst | 48 | |
| `pl_ui_render` + `st7789_blit_framebuffer` | 60 | blit measured 38.6 ms (pico-link-14l), rounded up |
| Console output: ~6 `pl_log` lines x `PICO_STDIO_USB_STDOUT_TIMEOUT_US` 2 ms | 12 | `CMakeLists.txt:144` |
| Frame pacing sleep | 16 | `main.c:302` |
| **Worst legitimate iteration** | **536** | |
| Round up | 600 | |
| x3 safety factor (unmeasured jitter, BTstack IRQ preemption at 0xFF, future codecs) | **1800** | |
| **Chosen** | **2000** | |

2000 ms is 12 % of the 16.777 s hardware ceiling (`watchdog.c:67`) — room to grow
if LDAC's encode cost lands heavier than SBC's.

**Long BTstack operations do not enter this budget**: everything the superloop
calls into BTstack from thread context (`pl_bt_poll_commands` ->
`gap_inquiry_start`, `pl_a2dp_connect`) queues an HCI command and returns; the
10 s inquiry window is event-driven, not blocking. **`cyw43_arch_init()`
(`main.c:263`) is the one boot-time call that could not be bounded statically** —
see step 0.

### Where the feed lives

`pl_wdt_service()` is called **exactly once**, from thread context, in the
superloop, after `pl_a2dp_report()` (`main.c:434`) and **before** the pacing
sleep (`main.c:449`). Nowhere else.

**Feeding from a timer or IRQ is explicitly forbidden**, and this is the
load-bearing constraint of the whole design: the 1 ms alarm and the 0xC0 worker
keep running when the superloop is wedged (that is their entire point), so a feed
there would reduce the watchdog to "is the timer peripheral alive". Symmetrically,
a superloop-only feed with no staleness table is blind to a dead 0xC0 worker or a
stopped BTstack run loop, since those failures leave the loop happily rendering.
**Hardware timeout catches "stopped executing"; the staleness table catches "still
executing, no longer doing its job."** Both are required; neither is sufficient.

### Reset behaviour

- **A watchdog reset never reaches BOOTSEL.** `_watchdog_enable` programs
  `PSM_WDSEL` for a full chip reset except ROSC/XOSC (`watchdog.c:48`), and with
  `scratch[4] != 0xb007c0d3` the boot path is the regular flash boot
  (`watchdog.c:96-108`). This is structurally different from `usb_reset.c`'s
  deliberate paths: `RESET_REQUEST_BOOTSEL` calls `rom_reset_usb_boot_extra`
  (`usb_reset.c:77`) — the only BOOTSEL route, reached only from a host-initiated
  vendor control request; `RESET_REQUEST_FLASH` (`usb_reset.c:82`) uses the same
  regular-flash `watchdog_reboot(0,0,...)` we use. Nothing in `pl_wdt` may ever
  call `reset_usb_boot`.
- **The one existing in-field BOOTSEL hazard is in the panic recorder:**
  `panic_recorder.c:131-144` routes a *recursive* panic to `reset_usb_boot(0,0)`.
  `pl_wdt` must therefore use a **separate entry point** that does not touch
  `scratch[3]`, or a watchdog trip would poison the retry flag and send the next
  genuine panic to BOOTSEL in a user's hands. Do not reuse
  `pl_panic_arm_record_and_reboot`.
- **Distinguishing reset causes at boot**, in `pl_wdt_report_boot_reason()`,
  *before* arming:
  - `watchdog_hw->reason == 0` -> power-on / brown-out (scratch is not retained
    across a true power cycle — reasoning banked at `panic_recorder.c:315-329`).
  - `reason != 0` and our WDT magic in `scratch[0]` -> supervised stale-subsystem
    trip, with the subsystem name.
  - `reason != 0` and `scratch[4] == 0x6ab73121` (`watchdog_enable_caused_reboot()`,
    `watchdog.c:123-125`) with no magic -> **unattributed hardware expiry**: the
    superloop itself died before the supervisor could attribute it. A distinct,
    valuable diagnosis — print it as such.
  - `reason != 0`, `scratch[4] == 0` -> a deliberate `watchdog_reboot` (our stale
    trip, the panic recorder's step 4, or `usb_reset.c:82`).
  - Use `watchdog_hw->reason` directly, **not** `watchdog_caused_reboot()`, for the
    reason `panic_recorder.c:315-329` documents: on RP2350 it also demands
    `rom_get_last_boot_type() == BOOT_TYPE_NORMAL`, false on the first boot after
    a reflash.

### Coexistence with the panic recorder

All 8 scratch registers are already spoken for, so **do not invent a parallel
record — extend the existing one.**

- `scratch[0]`: add `PL_PANIC_MAGIC_WDT 0x504c5744` ("PLWD").
- `scratch[1]`: stale subsystem id (`pl_wdt_subsys_t`).
- `scratch[2]`: observed staleness in ms.
- `scratch[3]`: **untouched by the watchdog path.** It is the panic recorder's
  retry/BOOTSEL-escalation flag; writing it is how you ship a BOOTSEL-in-the-field
  bug.
- `scratch[4..7]`: SDK-owned; `pl_wdt_arm()` touches them only via
  `watchdog_enable()`, once.
- `pl_panic_report_and_clear()` gains a `PL_PANIC_MAGIC_WDT` case and **clears the
  record as it does for the others** — so a trip is reported exactly once and a
  later genuine panic is not misread.
- **Ordering footgun, write it into the code as a comment:**
  `pl_wdt_report_boot_reason()` and `pl_panic_report_and_clear()` must both run
  *before* `pl_wdt_arm()`, because arming stamps `scratch[4]` with
  `WATCHDOG_NON_REBOOT_MAGIC` and destroys the evidence they read.
- A watchdog reboot **preserves** a pending panic record, because it never writes
  `scratch[0..3]` unless it is itself the cause.

### Debug vs release

**Armed by default in every build, including debug, with an explicit
`-DPL_WATCHDOG=OFF` opt-out.**

- A watchdog only armed in release is a watchdog whose behaviour is never
  exercised before it ships. Every hang this project has paid for was found on the
  bench, not in the field.
- `pause_on_debug = true` at the arm site (`watchdog.c:50-58`) — free insurance
  against an SWD halt tripping it. This deliberately differs from the panic
  recorder's `false` (`panic_recorder.c:124`), which is correct there: a panic must
  recover even under a debugger.
- The real cost is evidence destruction — a trip mid-capture reboots the board and
  the state is gone. The breadcrumb is the mitigation: every trip is
  self-documenting on the next boot, so a reboot mid-capture *is itself a finding*.
- **`PL_DEBUG_REMOTE` is not a factor and must not gate this.** Coupling watchdog
  arming to a *flash-tooling* flag would be exactly the accidental coupling this
  seam should not acquire. One dedicated `PL_WATCHDOG` option, defaulting `ON`.

### Non-goal, stated so it cannot drift

The watchdog is **not** the mitigation for the TinyUSB ISO-OUT defect, and must
never be cited as one. The 1 ms worker is that mitigation. A watchdog that reboots
the board every few minutes because the audio path is broken is a *worse* outcome
than a hang, because it converts a loud, diagnosable failure into a
tolerable-looking one. Therefore: every trip prints a line, and `pl_wdt_report()`
prints per-subsystem *margin* every second so degradation is visible long before a
trip.

## Alternatives considered

| Alternative | Verdict |
|---|---|
| Naive `watchdog_update()` at the top of the superloop | **Rejected.** Blind to the 0xC0 worker and the BTstack run loop — i.e. blind to every failure mode this firmware has actually suffered. |
| Feed from the 1 ms timer / 0xC0 worker | **Rejected explicitly.** Those keep running when the superloop is dead; converts the watchdog into a peripheral-liveness check. |
| Core1 as an independent supervisor (`pico-link-1rp`'s shape) | **Rejected.** cz0.6 redecided single-core; core1 is never launched (`main.c:255-258`, matching USBPods). A second core reintroduces the cross-core visibility problem 1rp was filed about. |
| 64-bit deadline stamps per subsystem instead of counters | **Rejected.** Torn reads across the IRQ/thread boundary on M33. |
| Stop feeding (starve the dog) instead of `watchdog_reboot` on a detected stale subsystem | **Rejected as the primary path** — keeps executing wedged code for up to another 2 s. Retained implicitly as the backstop when the supervisor itself never runs. |
| A separate RAM/scratch region for the watchdog breadcrumb | **Rejected.** No free scratch, and "why did the last boot end" is one question with one answer channel. |

## Consequences

- The 0xC0 hot path gains **one volatile increment in two places** — no new IRQ,
  no priority change, no timer change. `usb_pump` timing is untouched, as required.
- BTstack gains one 100 ms run-loop timer. Negligible, but it *is* a new permanent
  timer in a subsystem whose timing has been delicate; Tess should confirm
  `worst_tick_interval_us` in the `a2dp:` report line is unchanged before/after.
- The four deadline constants are, today, **engineering judgement, not
  measurement** — which is why the rollout observes before it trips.
- `main.c`'s halt-forever error paths (`pl_ui_create` failure `main.c:240`,
  `cyw43_arch_init` failure `main.c:265`) and the `PL_DIAG_*` loops sit *before*
  the arm point and remain deliberately un-watchdogged. Arming late is what keeps
  the diagnostics usable. Whether a failed `cyw43_arch_init` should reboot-and-retry
  instead of halting is a real question — **file it separately, do not scope-creep
  it here.**
- Boot (`tusb_init` -> `cyw43_arch_init` -> `pl_bt_init`) is unprotected in step 1.
  A deliberate staging choice, not an oversight.

## Implementation checklist (ordered)

**Step 0 — measure the one unbounded term.** In `main.c`, wrap `cyw43_arch_init()`
(`main.c:263`) in `time_us_64()` and `pl_log` the duration. Flash once, read the
number. It decides whether boot can later be brought under the same 2000 ms load.
*Do not skip — everything else is derived; this is not.*

**Step 1 — the module.** New `firmware/src/watchdog_sup.h` / `watchdog_sup.c`
implementing the API above. Constants: `PL_WDT_TIMEOUT_MS 2000`; deadlines
100 / 250 / 1000 / 500 ms per the table. All state file-static; `pl_wdt_kick` is a
`volatile uint32_t` `++` only. Gate the whole module's effect on `PL_WATCHDOG`
(kicks compile to nothing when off). Include the timeout arithmetic table as the
module doc comment — the number must not become unexplained folklore.

**Step 2 — the breadcrumb.** `panic_recorder.h/.c`: add
`PL_PANIC_MAGIC_WDT 0x504c5744`; add
`void pl_panic_record_watchdog_stale(uint32_t subsys, uint32_t stale_ms)
__attribute__((noreturn))` that writes `scratch[0..2]`, **does not touch
`scratch[3]`**, **never calls `reset_usb_boot`**, and calls
`watchdog_reboot(0, 0, 10)`. Extend `pl_panic_report_and_clear()`
(`panic_recorder.c:314`) with the WDT case and the reset-cause classification
above (raw `watchdog_hw->reason` + `scratch[4]`).

**Step 3 — producers.**
- `usb_pump.c`: `pl_wdt_kick(PL_WDT_USB_TIMER)` at the top of
  `pl_usb_pump_worker_irq` (after `usb_pump.c:48`, **before** the
  `mutex_try_enter` at :53); `pl_wdt_kick(PL_WDT_USB_TASK)` immediately after
  `tud_task()` (:57).
- `bt.c`: in `pl_bt_init` (`bt.c:432`), register a permanent 100 ms
  `btstack_run_loop` timer that kicks `PL_WDT_BTSTACK` and re-arms itself (same
  self-rearm idiom as `a2dp.c:553-554`).
- `a2dp.c`: `pl_wdt_kick(PL_WDT_MEDIA)` at the top of
  `pl_a2dp_media_timer_handler` (`a2dp.c:552`);
  `pl_wdt_set_enabled(PL_WDT_MEDIA, true)` in `A2DP_SUBEVENT_STREAM_STARTED`
  (`a2dp.c:914-915`); `...false)` in `STREAM_SUSPENDED` (`a2dp.c:958`),
  `STREAM_RELEASED` (`a2dp.c:970`) and `SIGNALING_CONNECTION_RELEASED`
  (`a2dp.c:982`).

**Step 4 — consumer + arm site.** `main.c`: call `pl_wdt_report_boot_reason()`
immediately before/after `pl_panic_report_and_clear()` (`main.c` ~:100) and
*before* arming; call `pl_wdt_arm()` right after `pl_bt_init(ui)` (`main.c:271`),
outside the `PL_DIAG_SKIP_BT` guard so diag builds are also armed; call
`pl_wdt_service()` and `pl_wdt_report()` once per iteration after
`pl_a2dp_report()` (`main.c:434`), before the pacing sleep (`main.c:449`).

**Step 5 — build.** `firmware/CMakeLists.txt`: add
`option(PL_WATCHDOG "Arm the hardware watchdog" ON)` -> compile definition; add
`src/watchdog_sup.c` to the target sources. `hardware_watchdog` is already linked
(`:175`) — no link change.

**Step 6 — observe-only first flash.** Ship with `PL_WDT_OBSERVE_ONLY`
**defined**: `pl_wdt_service()` feeds unconditionally and only *reports*
staleness. Run a full session on hardware — idle, scan, connect, stream, pause,
disconnect — and read the per-subsystem max-staleness line. The deadlines in the
table are judgement; this turns them into measurements.

**Step 7 — enable tripping.** Undefine `PL_WDT_OBSERVE_ONLY`, tighten any deadline
that measured far below its budget, and prove the trip path with a deliberate
fault-injection build (a `PL_DIAG_WDT_TEST` that removes the media timer or
disables the 0xC0 IRQ after N seconds). **Acceptance is the breadcrumb**: the board
must reboot and print the correct subsystem name on the next boot. Nothing less
proves the mechanism.

**Step 8 — hand `pl_wdt_blackout_begin/end()` to cz0.6.1.** The flash-write path
calls `begin` before disabling interrupts and `end` after re-enabling; `end`
re-bases every deadline stamp to `now` (during an IRQs-off erase the IRQ-driven
subsystems genuinely do not progress, and skipping that re-base is a guaranteed
false trip on the first save). This is the only integration cz0.6.1 needs, and it
changes no `usb_pump` timing.

## Could not verify

1. **The bead texts** — the architect session had no Bash, so `bd show` for `ufh`,
   `cz0.6`, `cz0.6.1` was not run. If cz0.6 fixes a different feed site or timeout,
   it supersedes this.
2. **`cyw43_arch_init()` duration** — unbounded from static reading; step 0 closes it.
3. **The 400 ms erase / 3 ms page-program figures** are generic SPI-NOR datasheet
   maxima, not measured on this board's flash part. cz0.6.1's own numbers win if
   they differ.
4. **macOS behaviour when idling in alt-setting 1** — the reason USB-audio packet
   flow is report-only rather than a reset trigger.
5. **`PL_DEBUG_REMOTE` did not exist on `main`** when this was written (it landed
   with the `cd3` merge on 2026-08-30). Re-check before relying on its absence.
6. **A live contradiction worth a separate bead:** `panic_recorder.c:224` states
   "NDEBUG is not defined anywhere in firmware/CMakeLists.txt, so `assert()` is live
   in the shipped build". The measured fact is the opposite (pico-sdk forces
   `CMAKE_BUILD_TYPE=Release`), which would make the `__assert_func` override at
   `panic_recorder.c:229` dead code in the default build. Not this bead's scope;
   nothing in this design depends on `assert()`.
7. **File-state oddity:** a first read of `firmware/src/a2dp.c` returned an older
   revision (~600 lines, pre-`pico-link-pbv`) than subsequent reads of the same path
   (~1130 lines). All line citations come from the **later, larger** revision. Ruby
   should re-confirm line numbers before editing.
