# Device page: the C/Rust seam — codec pinning, per-device settings, live signals

Bead `pico-link-ay0` (epic), the seam half. Author: Ada (architect), 2026-09-02.
Companion to `.planning/design/2026-09-02-device-page.md` (Uma) — this document
answers its **section 10 "For Ada"** list, all eight items, and adds four seam
findings Uma could not have seen from the UX side.

Fern owns the widget model in parallel. Nothing here designs a widget.

---

## 0. The answers, in one table

| § 10 item | Ruling | ABI cost | Tier |
|---|---|---|---|
| 1. Set-pin command keyed by address | `PlCommandTag::SetDeviceCodecPref = 7`, whole-value (no mask) | additive, **no** `PL_COMMAND_ABI_VERSION` bump | 1 |
| 2. Bypass the 2s settle | Urgent flag bypasses settle **and** the 10s rate limit; the **streaming gate is not bypassable** — see §4, this is the one place Uma's requirement cannot be fully met today | none | 1 |
| 3. Availability needs three states | New additive tag `CodecAvailability{addr, codec_id, state}`, **RAM-only, per-session**, never persisted | additive tag, no bump | 1 |
| 4. `CodecChanged` carries rate + depth | Yes | **`PL_EVENT_ABI_VERSION` 4 → 5** | 1 |
| 5. `USB IN` needs its own event | Yes, and it is cheap enough for Tier 1 (~30 lines) | additive tag, no bump | 1 |
| 6. A2DP stream-state signal | New additive tag `A2dpStreamStateChanged{state}` | additive tag, no bump | 1 |
| 7. "Pin not honoured" signal | Rides on `CodecChanged` as `pin_outcome` + `pinned_codec_id` | part of the 4 → 5 bump | 1 |
| 8. LDAC quality without teardown | **Yes.** `ldacBT_set_eqmid` is documented and implemented as callable at any time after init. The quality picker's reconnect confirm **disappears**. | none | 1 |

**ABI verdict, stated plainly as asked:** `PL_EVENT_ABI_VERSION` goes **4 → 5**.
`PL_COMMAND_ABI_VERSION` stays **2**. `PL_PERSIST_SCHEMA_VERSION` stays **1** —
confirmed below (§3.1). `firmware/include/pico_link_ui.h` is regenerated by
cbindgen; if `PL_EVENT_ABI_VERSION` in that header still reads 4 after the
change, the change did not land.

Two payload shapes change non-additively and they must land in **one** commit so
one bump covers both: `PlCodecChangedPayload` (§2.3) and
`PlPairedDeviceUpsertedPayload` (§2.2).

## 1. Four findings Uma could not have seen

These are the load-bearing ones. Items 1 and 2 are defects-in-waiting in code
that is already merged.

### 1.1 `codec_id` must be a pinned per-row identity, never the array index

`firmware/src/codec_table.c`'s own header comment: *"ARRAY ORDER is the
preference order a2dp.c's CAPABILITIES_COMPLETE handler actually walks"*, and
the whole point of the table (Andreas's 2026-08-29 ruling) is that adding a
codec is a new row, not surgery. Rows will be reordered — that is the design.

`pl_persist_device_record_t::codec_id` is a **flash-persisted** byte. If it
means "index into `PL_CODECS`", then the day AAC is inserted between LDAC and
SBC, every user who pinned SBC silently becomes pinned to AAC. Nothing detects
it, the CRC is fine, the record is "valid", and the UI confidently displays the
wrong promise. That is a stored corruption of user intent produced by a routine,
sanctioned change.

**Ruling.** Add `uint8_t codec_id` to `pl_codec_t` (`codec_table.h`), with
values pinned in the header and never reused:

```
0 = reserved: "Automatic" / "unset". Never a table row.
1 = SBC
2 = LDAC
3.. = future rows, allocated here and never recycled
```

`pl_a2dp_init` (which already walks `PL_CODECS` to create endpoints) asserts at
boot that every row's `codec_id` is nonzero and unique, and `pl_log`s loudly if
not. This is the cheapest possible guard against the one mistake that costs a
flash migration.

Cost of the alternative (index-as-id): zero today, a schema migration and a
class of silent wrong-codec bug later. This is the "cheap and wrong" shortcut in
this bead; take the pinned id.

### 1.2 `ldac_quality == 0` collides with `LDACBT_EQMID_HQ == 0`

`LDACBT_EQMID_HQ` is literally `0` (`firmware/vendor/libldac/inc/ldacBT.h:129`).
The stored byte defaults to 0 on every existing record. If the stored value is
the raw EQMID, then "the user has never chosen" and "the user explicitly chose
990 kbps" are the same byte, forever, unrecoverably.

**Ruling.** The stored `ldac_quality` is **1-based and is not an EQMID**:

```
0 = unset -- use whatever codec_ldac.c configures (today LDACBT_EQMID_HQ)
1 = 990 kbps  (maps to LDACBT_EQMID_HQ)
2 = 660 kbps  (maps to LDACBT_EQMID_SQ)
3 = 330 kbps  (maps to LDACBT_EQMID_MQ)
4 = Adaptive  (reserved, NOT implementable today -- see §6)
```

The mapping to EQMID lives in exactly one place, `codec_ldac.c`. Ruby must not
restate §3.2's numbers or this table's kbps figures anywhere else — the kbps
strings the UI shows come from `ldacBT_get_bitrate()` at run time (standing
ruling `pico-link-qx8`: ask the library, never restate its table). The numbers
above are the *labels on the choices*, which are fixed vocabulary.

### 1.3 A settings write must not bump `mru_seq` — and today every write does

`pl_persist_do_write` (`persist.c:485`) unconditionally does
`rec.mru_seq = s_next_mru_seq++`, documented as *"every write, by construction,
means 'this device was just used'"*. That was true when the only writer was
pairing.

It is false for a codec pin, and the consequence is not cosmetic: `core`'s
auto-reconnect policy is `paired.iter().max_by_key(|d| d.mru_seq)`
(`PlStoreLoadedPayload`'s doc comment). Pinning a codec on a device you are not
connected to would make it the boot reconnect target. Setting a preference is
not using a device.

**Ruling.** A second, narrower entry point that does **not** touch `mru_seq`:

```c
// persist.h -- NEW. Updates per-device settings on an ALREADY-REMEMBERED
// device. Does NOT bump mru_seq (setting a preference is not using a device
// -- see the design's 1.3) and does NOT create a slot: returns false if no
// slot currently holds `addr`.
//
// Calling contract: identical to pl_persist_execute_pending_write --
// cyw43/BTstack async_context ONLY, via bt.c's pending queue.
bool pl_persist_write_device_settings(const uint8_t addr[6], uint8_t codec_id, uint8_t ldac_quality);
```

Implemented by refactoring `pl_persist_do_write` into a shared RMW core that
takes an explicit "which fields does this call carry" descriptor, so there is
one read-CRC-modify-write-CRC implementation, not two. Two independently
written RMW paths over the same on-flash struct is precisely how a CRC-checked
store starts producing "corruption" nobody can reproduce.

Refusing to create a slot is deliberate: the device page is only reachable for
a remembered device or the connected one, and a connected device is written at
pairing time. There is no legitimate "pin a codec on a device we have never
stored" path, and inventing one would let a pin consume one of eight slots
without pairing.

### 1.4 `s_boot_devices` is populated once at init and never updated by a write

`persist.c:111` — the boot snapshot is filled by `pl_persist_init`'s load loop
and read by `pl_persist_boot_device_count/at`. `pl_persist_do_write` updates
`s_slot_occupied` / `s_slot_addr` but **not** `s_boot_devices`.

Today that is harmless (nothing reads the snapshot after boot). It stops being
harmless the moment a2dp.c reads the pin from it at connect time (§3.3): a pin
set at 10:00 would not take effect until the next power cycle, which reads
exactly like "the setting didn't save" — the failure this whole bead exists to
prevent.

**Ruling.** The snapshot becomes the live in-RAM mirror of the store, not a
boot artifact: rename it in spirit (`s_slot_record[]`), extend it with
`codec_id` and `ldac_quality`, and have the shared RMW core update the mirror
entry it just wrote, inside the same critical section it already uses for
`s_slot_addr`. `pl_persist_boot_device_*` keep working unchanged on top of it.

## 2. The seam surface, concretely

### 2.1 The command (§10 item 1)

```rust
// ui-ffi/src/lib.rs
pub enum PlCommandTag { /* ... */ SetDeviceCodecPref = 7 }

#[repr(C)] #[derive(Clone, Copy)]
pub struct PlSetDeviceCodecPrefPayload {
    pub addr: [u8; 6],
    /// 0 = Automatic. Otherwise a pinned `pl_codec_t::codec_id` (design 1.1).
    pub codec_id: u8,
    /// 1-based, NOT an EQMID (design 1.2). 0 = unset.
    pub ldac_quality: u8,
}
// added to PlCommandPayload as `set_device_codec_pref`
```

Keyed by `addr`, as required — the page is reachable for a device that is not
connected. New tag, so **additive: `PL_COMMAND_ABI_VERSION` stays 2.**

**Whole-value, not a field mask.** `core` owns the model and, once §2.2 lands,
always knows both current values; sending both every time makes this a
last-writer-wins write of a complete value. A mask would introduce a diff
protocol across the seam whose only failure mode is silent (a mask bit set
wrong writes a stale value with no error), for the sake of saving one byte.

**C's handler** (`bt.c`'s `pl_bt_poll_commands`, thread context) does two things
and neither of them touches flash or libldac directly:

1. `pl_bt_pending_push(PL_BT_PENDING_WRITE_DEVICE_SETTINGS, addr)` — carrying
   `codec_id`/`ldac_quality` in the pending entry (the entry struct gains two
   bytes; `PL_BT_PENDING_CONNECT`/`FORGET` already set the precedent of
   tag-specific fields).
2. If the device is the currently connected one **and** only `ldac_quality`
   changed, `pl_bt_pending_push(PL_BT_PENDING_SET_LDAC_QUALITY, addr)` — §5.

Both drain on the cyw43/BTstack async_context via `pl_bt_pending_service`, which
is the existing sanctioned path for exactly this. No new mechanism, no new
context, no new IRQ-context Rust call.

### 2.2 The echo: `PairedDeviceUpserted` gains the settings fields

`persist.c`'s single-writer rule ("no echo means no row") means `core` learns
what a record holds only from `PlEventTag::PairedDeviceUpserted`, pushed from
inside `pl_persist_do_write`. `core::PairedDevice` therefore has no way to know
a device's pin — which the CODEC row must show on a **disconnected** device
(Uma §3.0's sharpened degraded rule: a stored setting never dashes).

Two shapes were considered:

- **(a) Extend `PlPairedDeviceUpsertedPayload`** with `codec_id` and
  `ldac_quality`. Non-additive → `PL_EVENT_ABI_VERSION` 4 → 5.
- **(b) A separate additive `DeviceSettingsChanged{addr, codec_id, ldac_quality}`
  tag.** No bump.

**Take (a).** The record is one object; the event that echoes it should be that
object. (b) is cheaper by exactly one integer literal and buys a permanent
two-events-describe-one-record ordering hazard: boot must push both per device,
and any path that pushes one without the other leaves `core` holding a record
half-updated with no way to notice. The bump costs nothing — nothing outside
this repo speaks this ABI, and this is one coordinated build.

`core::PairedDevice` gains `codec_id: u8` and `ldac_quality: u8`. Keep them as
raw bytes with a `CodecPin` newtype/enum at the render boundary; `core` must not
grow a codec-identity table (Andreas's no-branch-on-codec-identity ruling
applies on both sides of the seam — `core` already only ever displays the
`display_name` string C sends).

### 2.3 The "pin not honoured" signal (§10 items 4 + 7)

The outcome is known at exactly one place: a2dp.c's
`A2DP_SUBEVENT_SIGNALING_CAPABILITIES_COMPLETE` walk (`a2dp.c:1410-1497`), which
is the only code that knows what was pinned, what the remote offered, and what
`set_config_*` actually accepted. It is also the site the pin itself modifies
(§3.3). Putting the signal anywhere else means a second place that has to
re-derive the same fact.

It rides on `CodecChanged`, which is already keyed by `addr` and already fires
from `pl_a2dp_finish_codec_negotiation` (`a2dp.c:1142`):

```rust
#[repr(C)] #[derive(Clone, Copy)]
pub struct PlCodecChangedPayload {
    pub addr: [u8; 6],
    pub name: [u8; 16],
    pub name_len: u8,
    pub nominal_bitrate_bps: u32,
    // NEW (item 4) -- both already live in `pl_codec_format_t`, which
    // a2dp.c holds as s_ctx.format at this exact point.
    pub sample_rate_hz: u32,
    pub bits_per_sample: u8,
    // NEW (item 7). Plain u8, checked-converted on the Rust side, per this
    // module's standing convention for every union-member discriminant.
    //   0 = NoPin        -- Automatic; an SBC result here is an ordinary
    //                       negotiation outcome, NOT a broken promise
    //   1 = Honoured     -- pinned codec is the one that configured
    //   2 = FellBack     -- pinned codec could not be honoured; this is
    //                       the amber state
    pub pin_outcome: u8,
    /// The `codec_id` that was pinned, so the UI can name it in the
    /// picker's explanation ("you pinned LDAC"). 0 when `pin_outcome == 0`.
    pub pinned_codec_id: u8,
}
```

This is the field that makes "you pinned LDAC, the headphones refused, you are
on SBC" distinguishable from "Automatic negotiated SBC". Those are the two
states the design refuses to let look alike, and `pin_outcome` is the only thing
that separates them — an SBC `name` string cannot, and neither can the absence
of LDAC in the availability list (a device that never offered LDAC and a user
who never pinned it produce identical availability).

`core::ConnectedCodec` gains `sample_rate_hz`, `bits_per_sample`, `pin_outcome`,
`pinned_codec_id`. `pin_outcome == FellBack` is what drives Uma's amber CODEC
trailing, the amber Home hero, and Home's `why?` label — one flag, three
surfaces, no re-derivation.

### 2.4 Per-device codec availability, three states (§10 item 3)

```rust
pub enum PlEventTag { /* ... */ CodecAvailability = 13 }

#[repr(C)] #[derive(Clone, Copy)]
pub struct PlCodecAvailabilityPayload {
    pub addr: [u8; 6],
    pub codec_id: u8,
    /// 0 = Unknown ("not yet known")   -- ACTIVATABLE in the picker
    /// 1 = Available ("always available" for SBC; offered for others)
    /// 2 = NotOffered ("not offered")  -- disabled
    /// 3 = Refused ("refused")         -- disabled; offered but set_config
    ///     failed or the config could not be honoured (e.g. the remote's
    ///     LDAC SEP without 48kHz/stereo -- a2dp.c:1478)
    pub state: u8,
}
```

New tag → **additive, no bump.** One event per `PL_CODECS` row, pushed from the
CAPABILITIES_COMPLETE walk (2 events today, 3-4 later; the ring has 31 usable
slots and drains every superloop iteration — negligible).

**Availability is RAM-only and per-session; it is never persisted.** A device
whose AVDTP discovery has not completed *this boot* reads `Unknown` / "not yet
known" and stays activatable, exactly as Uma requires — a bool cannot express
that, and neither can a persisted value, because a stale persisted "not offered"
from six weeks ago would be indistinguishable from a fresh fact. `core` holds it
in a small per-address map that is cleared on `LinkStateChanged` away from
`Connected` only for the device that dropped. Absent = `Unknown`, so the default
is honest with no allocation and no store bytes.

The reason strings (`not offered` / `not yet known` / `refused` /
`always available`) are **`core`'s**, chosen from Uma's fixed ≤14-char
vocabulary and keyed off `state`. They are not sent over the seam — they are UI
copy, and the seam carries facts.

### 2.5 `USB IN` (§10 item 5) — Tier 1, and here is the cost

Ada's call, as asked: **build it now.** It is roughly 30 lines and everything it
needs already exists in C.

```rust
pub enum PlEventTag { /* ... */ UsbAudioStreamChanged = 14 }

#[repr(C)] #[derive(Clone, Copy)]
pub struct PlUsbAudioStreamChangedPayload {
    pub active: u8,            // 0/1, this module's bool convention
    pub sample_rate_hz: u32,   // pl_usb_audio_sample_rate()
    pub bits_per_sample: u8,   // CFG_TUD_AUDIO_FUNC_1_FORMAT_1_RESOLUTION_RX
}
```

Pushed from `usb_audio.c`'s `tud_audio_set_itf_cb` (alt 1 selected, `usb_audio.c:211`),
`tud_audio_set_itf_close_EP_cb` (alt 0, `usb_audio.c:236`), and the clock-set
path (`usb_audio.c:123`) — all USB IRQ context, all pushing into
`pl_bt_ring_push`, which is explicitly MPSC and interrupt-safe (its whole body
runs inside `save_and_disable_interrupts`). **No new IRQ-context Rust call**:
the ring is the sanctioned producer and `pl_bt_drain_events` remains the only
thing that calls `pl_ui_push_event`.

Rationale for Tier 1 rather than a dash: Uma cut `SIGNAL` because a permanently
dashed field is a standing admission of ignorance on the credibility surface,
and dashed `USB IN` only escapes that argument for as long as it is genuinely
about to be built. Shipping a row whose value exists in a getter we already call
every superloop, and dashing it, is the same defect with a longer excuse.

**Do not derive it from the codec format.** Uma is right and the reason is
structural, not stylistic: `pl_codec_format_t.sample_rate_hz` is the *A2DP*
side. SBC can negotiate 44100 while the host sends 48000; the whole point of the
row is to show the two ends of the pipe separately.

### 2.6 A2DP stream state (§10 item 6)

```rust
pub enum PlEventTag { /* ... */ A2dpStreamStateChanged = 15 }

#[repr(C)] #[derive(Clone, Copy)]
pub struct PlA2dpStreamStateChangedPayload {
    pub state: u8, // 0 = Idle, 1 = Streaming
}
```

Additive, no bump. Pushed from the three `s_ctx.state` transitions in a2dp.c
(`a2dp.c:1811, 1822, 1897/1911/1956`), all already in the BTstack packet handler
(async_context, ring-safe). `PL_A2DP_MEDIA_PRIMING` maps to `Streaming` — it is
the state where the transport is open and packets are about to flow, and Uma's
row has two values, not three. The third value (`—`) is `core`'s own, derived
from `LinkState != Connected`; do not send a "not connected" state over this
event and create two sources of truth for connectedness.

## 3. Persistence

### 3.1 Schema version stays 1 — confirmed, as asked

`pl_persist_device_record_t` (`persist.c:64-75`) already holds `codec_id`,
`ldac_quality`, `volume`, `flags`, `preset_id`. `pl_persist_do_write` is
read-modify-write and explicitly documents these five as riding through
untouched (`persist.c:487-490`). Existing records read back with `codec_id == 0`
and `ldac_quality == 0`, which are exactly the "Automatic" and "unset" sentinels
§1.2 and §1.1 define. The CRC covers the whole struct and does not change shape.

**No schema bump, no migration, no `PL_PERSIST_SCHEMA_VERSION` change.** This is
the one thing in this bead that is already paid for.

Do **not** spend `flags` on anything here. "Pin not honoured" is live state, not
stored state — persisting it would let a stale anomaly from a previous
connection colour the UI amber on a fresh one.

### 3.2 How the write bypasses the settle — and the part that cannot

`pl_persist_service` (`persist.c:670-694`) gates in this order:

```
1. nothing pending            -> return
2. pl_usb_audio_streaming() || pl_a2dp_streaming()   -> return     <-- HARD
3. if !urgent: 2s settle AND 10s rate limit          -> maybe wait <-- soft
4. enqueue onto bt.c's pending queue; the write happens on the
   async_context in pl_bt_pending_service
```

`pl_persist_request_urgent_flush()` already skips step 3 entirely. So the answer
to "how does the pin write bypass the 2s settle while still honouring
async-context-only" is: **it uses the existing urgent path, unchanged, through
the existing pending queue.** Every flash write still happens in
`pl_bt_pending_service`, on the cyw43/BTstack async_context, never in thread
context. Nothing new is invented; the reentrancy contract in `persist.h` is
untouched.

**Step 2 is not bypassable, and that is a physical constraint, not a policy.**
A flash write is up to three ~3ms blackouts with interrupts disabled; USB
audio's ISO-OUT re-arm has a 2ms bar and exactly one miss is *permanent*
(`audio_device.c:759-762`). Writing while the host streams does not risk a
glitch, it risks the deaf-endpoint wedge that cost this project multiple
sessions.

So the honest statement of the guarantee, which Ruby must implement and Uma
should know:

> **A codec pin is written to flash the moment nothing is streaming — which is
> immediately, in the common cases of pinning on a disconnected device or with
> the host idle. If the host is actively streaming USB audio when the pin is
> set, the write is staged in RAM and lands as soon as streaming stops.**

That residual window is real, and Uma's requirement ("a pin the user just set
and then unplugged must not evaporate") is *not* met inside it. Two ways to
handle it; I recommend both:

1. **Tier 1 — make it visible, per the design's own rules.** `core` applies the
   choice to its model optimistically (so pressing LDAC changes the row
   immediately) but marks it **unconfirmed** until the
   `PairedDeviceUpserted` echo arrives. An unconfirmed pin renders in
   `STATUS_WARNING`, the same amber that already means "you did not get what you
   asked for", resolving to `TEXT_PRIMARY` on the echo. This costs zero new
   widget capability: it is a trailing colour, exactly like the fell-back state.
   **Handing this back to Uma as a question, with that as my recommendation** —
   it is a visual state she has not specified and I am not the one who should
   invent copy for it. Note for whoever builds it: the resolve happens on an
   event, so the dirty flag is set for free (`App::handle_event` marks dirty);
   nothing here needs `redraw_after`.

2. **Tier 2 — remove the window.** File a bead: make the USB ISO path
   RAM-resident (`__not_in_flash_func` across the TinyUSB ISO OUT ISR and its
   call graph) and use real multicore flash lockout instead of a blanket
   interrupt disable, so a flash write does not stop USB servicing. This is a
   known technique, not research, and it also retires `pico-link-lmf` (the
   pairing-time carve-out, which is the *same* window seen from a different
   caller). It is real work — an audit of the whole ISO call graph, core 1
   brought up — and it is emphatically not MVP. **Relate the new bead to
   `pico-link-lmf`; they are one problem.**

This is a *not built yet*, not an *impossible*. Uma designs the target UX; the
target is that pins save instantly, always. Today's firmware has one window
where it cannot, and that window has a name, a cause, a fix, and a bead.

### 3.3 How the pin actually changes what gets negotiated

At `A2DP_SUBEVENT_SIGNALING_CAPABILITIES_COMPLETE` (`a2dp.c:1410`), before the
`PL_CODECS` walk:

```c
uint8_t pinned = 0, quality = 0;
pl_persist_get_device_settings(s_ctx.connect_addr, &pinned, &quality); // in-RAM mirror, no flash read
```

Then the walk gains exactly one rule, and no codec-identity branch:

- `pinned == 0` → walk unchanged. Today's behaviour, byte for byte.
- `pinned != 0` → **first** try only the row whose `codec_id == pinned`. If it
  configures, `pin_outcome = Honoured`. If it does not (not offered, or
  `set_config_*` failed, or the config could not be honoured), fall through to
  the normal preference-ordered walk **with the pinned row skipped**, and set
  `pin_outcome = FellBack`.

Falling through to the *full* walk rather than jumping straight to SBC matters:
if a user pins AAC on headphones that only do LDAC and SBC, "fall back to SBC"
would hand them a worse result than Automatic would have. Uma's rule is "falls
back to SBC and says so" because SBC is the terminating floor of the walk — and
it still is, because SBC is permanently last and mandatory. The walk *is* the
fallback; do not write a second one.

**Never refuse to connect.** The existing `if (!matched)` arm
(`a2dp.c:1494`) stays exactly as it is and keeps pushing
`PL_FAILURE_REASON_NO_A2DP_SINK` — that is "the remote offered nothing we can
do", which is a genuine failure and unrelated to pinning.

The accessor:

```c
// persist.h -- NEW. Reads the in-RAM slot mirror (design 1.4). No flash
// access, no allocation, safe from the async_context. Returns false and
// leaves the outputs untouched if `addr` is not remembered.
bool pl_persist_get_device_settings(const uint8_t addr[6], uint8_t *out_codec_id, uint8_t *out_ldac_quality);
```

**C reads the pin from its own store; `core` does not send it on `Connect`.**
`PlConnectPayload` carries `name` because C genuinely had no name (design
`2026-09-01-remembered-devices.md` §5.3). That reasoning does not transfer: C
owns the store and already has the pin. Riding it on `Connect` would create a
second copy of a persisted value and an ordering rule whose failure mode is
silent. `PlConnectPayload` is unchanged.

## 4. LDAC quality applies live — item 8 answered yes

`ldacBT.h:253-265`: *"The API function can be called at any time, after the
completion of initializing."* `ldacBT_api.c:288-304` confirms it — `ldacBT_set_eqmid`
validates and calls `ldacBT_set_eqmid_core`, which only updates `tgt_eqmid`,
`tgt_frmlen` and `tgt_nfrm_in_pkt` (`ldacBT_internal.c:206-218`). The actual
frame-length switch happens inside the encoder's own setup on a subsequent
encode, which is exactly the mechanism ABR uses. No AVDTP reconfigure, no
teardown, no reconnect.

**So the quality picker's reconnect confirm disappears.** Strictly better, and
worth telling Uma — it removes a confirm from a reversible action, which is the
same argument she used for the X rail.

Two constraints on the implementation:

1. **`ldacBT_set_eqmid` mutates encoder state that `encode()` reads in the
   cyw43/BTstack IRQ.** It must therefore run on that same context — new
   `PL_BT_PENDING_SET_LDAC_QUALITY` entry, drained by `pl_bt_pending_service`,
   exactly like the persist write. Never from thread context. It must **not** be
   called from `encode()` itself (`codec_table.h`'s no-allocation/no-blocking
   contract is about the hot path; adding a control call there is the wrong
   direction).

2. **The bitrate readout goes stale for one tick.** `hLdacBT->bitrate` is
   recomputed only when the frame length actually updates
   (`ldacBT_internal.c:334, 374`), which happens on a later encode, not inside
   `set_eqmid`. So: after a successful `set_eqmid`, set a flag, and on the
   **next** watchdog-heartbeat tick (100ms, same context) read
   `ldacBT_get_bitrate()` and push a fresh `CodecChanged`. 100ms of latency on a
   number, zero hot-path cost, and it still obeys `pico-link-qx8` — ask the
   library, never restate its table.

`codec_ldac.c`'s `init` also stops hardcoding `LDACBT_EQMID_HQ`
(`codec_ldac.c:141`) and reads the stored `ldac_quality` for the connecting
address, mapped through the one table in §1.2. Ruby: read the current default
from that line, do not take a number from any design document.

## 5. `Adaptive` is not implementable with the vendored libldac

This is a genuine cut and it needs saying before anyone builds the row.

`ldacBT_assert_eqmid` (`ldacBT_internal.c:196-203`) accepts **only** `HQ`, `SQ`
and `MQ`. `LDACBT_EQMID_ABR` (0x7F) is rejected by both `ldacBT_set_eqmid` and
`ldacBT_init_handle_encode`. The ABR controller is a *separate* Sony library
(`libldacBT_abr` / `ldacBT_abr.h`, referenced only in a `#ifdef` comment at
`ldaclib_api.c:459`) and is **not vendored in this repo**. ABR also requires
feeding the controller a live transmit-queue-depth metric every packet — which
this project does have material for (a2dp.c already tracks queue occupancy), but
which is a real pacing integration, not a flag.

**Classification: not built yet, not impossible.** `libldacBT_abr` is Apache-2.0
and vendorable on the same terms as libldac. File a bead.

**Tier 1 ruling:** the quality picker offers `990` / `660` / `330` as
activatable rows and `Adaptive` as a **disabled-but-focusable** row with the
reason `not yet built`. That is the exact capability Uma's §4 collapse already
requires for the codec picker — it reuses it rather than adding anything, and it
keeps the choice visible so the design's stated consequence (Home renders the
word `Adaptive`, `varies` in the picker) stays specified and unreachable rather
than being deleted and re-derived later. Reserve stored value `4` for it now
(§1.2) so no migration is needed when it lands.

Uma's Home-bitrate `Adaptive` word and the picker's `varies` note stay in the
design of record, unimplemented. That is the correct treatment of a designed,
not-yet-built target.

## 6. The remaining section-10 items, and what is out of scope

- **`LABEL` row with a fixed vocabulary** (Uma §7.1, deferred to Ada because it
  needs store bytes): it does **not** need a schema bump either. The record has
  a spare `flags` byte and `volume` is unused; a label is a 3-bit enum. But do
  **not** spend `flags` on it casually — `flags` is the only general-purpose
  byte left and a label deserves its own field. Correct answer: it needs a
  schema bump eventually, and it should ride *with* the next feature that also
  needs one (a preset store, most likely), not trigger one alone. Not this
  epic. File it, note the coupling.
- **`EQ PRESET`**: Uma's ruling (absent until the DSP exists) is right and the
  seam agrees — `preset_id` stays reserved and untouched, and
  `pl_persist_forget_device` already deletes only the device record, never a
  preset tag (`PL_PERSIST_KIND_PRESET` is a separate tag namespace). The
  invariant Andreas asked for is structurally satisfied today; no work needed,
  and a test should assert it before the preset store exists so it cannot
  regress silently.
- **Forget-route move** (Uma §9): pure `core`/render work, no seam change.
  `Command::ForgetDevice` and `PlCommandTag::ForgetDevice` already exist and are
  already wired end to end through `PL_BT_PENDING_FORGET_DEVICE`.

## 8. Risks

- **The ABI bump must be atomic.** Two payload reshapes, one bump. A partial
  landing gives a `PL_EVENT_ABI_VERSION` mismatch, and `pl_ui_push_event`'s
  guard makes that a **silent no-op** — the board renders a frozen UI with no
  error. Verify by cross-compiling the firmware, not by `cargo test`.
- **The dirty gate.** `pico-link-vxc` gates the blit on `pl_ui_dirty()`.
  Everything here arrives as an event, and `App::handle_event` marks dirty, so
  this is safe by construction — *except* the optimistic/unconfirmed pin state
  (§3.2 item 1), which is set by a local `A` press. That path must mark dirty
  itself or the row silently will not repaint.
- **Not re-litigating the streaming gate.** If anyone proposes writing flash
  during USB streaming to "make the pin save instantly", the answer is no; the
  fix is §3.2 item 2, and it is a separate bead with real work in it.
