# A2DP drain: decouple fill from send

**Bead:** `pico-link-85v` · **Author:** Ada (architect) · **Date:** 2026-08-30
**Status:** design of record for the A2DP media drain (supersedes the
one-packet-per-tick shape in `2026-08-29-a2dp-source-pipeline.md` sec 5)

Source-derived from `firmware/src/a2dp.c` at `cf8fcaa` (r44 + nzw merged),
`codec_table.h`, and pico-sdk 2.1.1's vendored BTstack. **No hardware was
available this session**; every claim is marked source-derived or
needs-measurement. The capture checklist EXTENDS
`.planning/design/2026-08-30-pcm-pacing.md` — it does not replace it.

## Context

Two facts fix this bead's scope, both established earlier today:

- Today's packet ceiling **does not bind for SBC** (~620 SBC frames/s capacity
  against 375 demand, 1.65x). `stop_packet_full_hot` should read 0.
- LDAC needs **140 packets/s at HQ, 93/s at SQ** against a ~88.5/s ceiling.
  This bead is LDAC's blocker, and only LDAC's.

The mechanism of the ceiling is **not** "one packet per grant". It is that a
tick which finds `sbc_ready_to_send` still true does **no filling at all** —
`a2dp.c:680-692`, where the `else` branch only increments
`ticks_send_pending`. Fill and send are coupled through a single buffer and a
single boolean.

Two constraints are load-bearing and survive unchanged:

1. **The `pl_log` ban** on everything transitively reachable from
   `pl_a2dp_media_timer_handler`, `pl_a2dp_fill_sbc_buffer` and
   `pl_a2dp_send_media_packet` (`a2dp.c:52-63`). One `pl_log` there takes
   `pl_usb_mutex`, the 0xC0 worker's `mutex_try_enter` fails, it skips a tick,
   and enough skipped ticks permanently kill the ISO-OUT endpoint
   (`pico-link-0d2`). Every new signal here is a counter read by
   `pl_a2dp_report` in thread context.
2. **No codec-identity branch** in the fill/send path (`codec_table.h:4-11`).
   Not "no switch on codec" — no *structure* that only one codec's shape
   satisfies. Today's send path violates the spirit of this at `a2dp.c:537`
   (`num_frames = bytes_in_storage / frame_bytes`), meaningful only for
   fixed-size frames. This design removes that.

## Decision

### D1 — A fixed ring of payload slots, filled by the timer, drained by the grant

Replace `sbc_storage` / `sbc_storage_count` / `sbc_ready_to_send` with:

    typedef struct {
        uint8_t  data[PL_A2DP_PAYLOAD_SLOT_BYTES]; // byte 0 reserved: payload header
        uint16_t len;      // bytes INCLUDING the reserved header byte
        uint16_t frames;   // accumulated during fill -- NOT derived by division
        uint32_t rtp_ts;   // stamped at SEAL, not at send
    } pl_a2dp_slot_t;

    pl_a2dp_slot_t tx[PL_A2DP_TX_QUEUE_SLOTS];
    uint8_t tx_head;      // slot currently being filled
    uint8_t tx_tail;      // next slot to send
    uint8_t tx_count;     // sealed, unsent
    bool    send_requested;

`SBC_STORAGE_SIZE` is renamed `PL_A2DP_PAYLOAD_SLOT_BYTES` (same value, 1030).
The `SBC_` prefix is a codec-identity smell in a file forbidden from having
one; the value is a payload-storage ceiling, not an SBC property.

**Fill** (`pl_a2dp_fill_sbc_buffer`, renamed `pl_a2dp_fill`). Stop conditions
become, in order: dwell, credit, **queue-full**, ring-empty. The old
packet-full stop is no longer a *stop*: when the head slot cannot take another
frame the loop **seals** it (`len`, `frames`, `rtp_ts` written; `tx_count++`;
`tx_head` advances), arms the send if needed, and **continues in the same
tick**. Only "no free slot" ends the loop.

**Seal** is one function with one call site: write len/frames/rtp_ts, advance
`rtp_next` by `frames * pcm_frames_per_encoded_frame`, advance `tx_head`,
increment `tx_count`, and if `!send_requested` set it and call
`a2dp_source_stream_endpoint_request_can_send_now`.

**Send** becomes: if `tx_count == 0`, count `spurious_grants`, clear
`send_requested`, return. Otherwise write the header byte into `data[0]`, call
`a2dp_source_stream_send_media_payload_rtp` with the slot's own `rtp_ts` and
`len`, advance `tx_tail`, decrement `tx_count`, and re-arm
`request_can_send_now` if the queue is still non-empty.

**The re-arm inside the grant handler is the whole fix, and it is legal.**
Source-derived and independently re-verified by the orchestrator,
`avdtp.c:546-552`: BTstack clears `stream_endpoint->request_can_send_now`
*before* dispatching to us, then immediately after our handler returns it
re-checks the flag and calls `l2cap_request_can_send_now_event` again if we set
it. Our re-request is the sanctioned path, and the next grant arrives as soon
as L2CAP has an ACL buffer — **not** at the next media tick. The drain becomes
ACL-credit-bound. *(How fast that is: needs-measurement, item (h).)*

`a2dp_source_stream_send_media_payload_rtp` copies into an L2CAP buffer, so the
slot is free the instant the call returns — no in-flight retention, no
DMA-lifetime hazard.

**Concurrency: none.** The media timer handler and the A2DP packet handler both
run in the BTstack run loop on the 0xFF background IRQ, and BTstack does not
re-enter its own run loop. `tx_head`/`tx_tail`/`tx_count` are therefore *not*
cross-context shared state like `pcm_ring` — plain non-volatile fields, no
barriers, no lock-free discipline. **State this in the code comment**, because
the visual similarity to `pcm_ring` invites someone to "harden" it later with
atomics that would be pure cost.

### D2 — Depth = 5, derived

Let `D` = per-tick dwell budget (D4), `E` = the row's `worst_case_encode_us`,
`F` = `frames_per_packet`.

- `B_tick` = max payloads sealed in one tick = `ceil(D / (E * F))`
  - SBC: `6000 / (800 * 7)` = 1.07 -> **2**
  - LDAC HQ: `4150 / (1100 * 3)` = 1.26 -> **2**
- Grant latency measured `< 1 tick` (`ticks_send_pending` read **0** for the
  whole pbv investigation). Budget one tick.

`N = 1 (head) + B_tick (sealed this tick) + B_tick (unsent from last tick) = 5.`

`PL_A2DP_TX_QUEUE_SLOTS = 5`, derivation in its doc comment, and — following
the `pico-link-r44` lesson that a silent clamp is worse than a loud one —
`B_tick` is **recomputed at STREAM_ESTABLISHED** from the actual negotiated
`frames_per_packet` and the active row's `worst_case_encode_us`. If
`1 + 2*B_tick > PL_A2DP_TX_QUEUE_SLOTS` the stream logs a WARNING (signalling
context, `pl_log` legal there) naming both numbers. No silent undersizing.

### D3 — RAM

`sizeof(pl_a2dp_slot_t)` = 1030 + 2 + 2 + 4 = 1038, padded to **1040**.
5 slots = **5200 B** replacing today's 1030 B: **net +4170 B**.

- `.bss`, inside the existing file-scope `static pl_a2dp_ctx_t s_ctx`. **No
  heap** — the IRQ-context contract forbids allocation.
- **SRAM, not PSRAM.** Written from a 0xFF IRQ and read synchronously by
  L2CAP; putting them behind the QMI/XIP cache adds unbounded-latency accesses
  inside the dwell budget for no benefit at this size.
- 5200 B against 520 KB SRAM is **1.0%**. Exact `.bss` delta is
  needs-measurement (read the map file, item (j)).

### D4 — Dwell: the bound, why it rises, and why 6000 stops being magic

**What changes.** Today the fill loop nearly always stops at packet-full
(`a2dp.c:468-482`) long before the dwell budget — 7 frames x 574 us is
~4.0 ms. `stop_dwell` reads 0 not because 6000 is generous but because a
*different* limit always fired first. Removing that limit makes
`PL_A2DP_MAX_ENCODE_DWELL_US` **reachable for the first time**. That is exactly
what `pico-link-baj` was filed about: an underived constant, harmless while
latent. It stops being latent here, so this design resolves it rather than
adding a second one.

**The new bound**, evaluated per tick inside the fill loop:

    dwell_budget_us = min( PL_A2DP_MAX_ENCODE_DWELL_US,      // backstop
                           CATCHUP_K * owed_frames * E,      // work bound
                           (2 * elapsed_us) / 3 )            // duty bound
                      floored at E                           // never deadlock

`owed_frames = samples_owed / pcm_frames_per_encoded_frame` at tick entry
(already computed — no new clock, no new `time_us_64()`), `E` from the codec
row, `CATCHUP_K = 2`.

- **Work bound** — the loop never needs more than *twice* the work real time
  has owed it; beyond that is not catch-up, it is running ahead of the sink.
  `K = 2` retires a backlog at twice real time: a 100 ms stall absorbs in
  100 ms.
- **Duty bound** — the fill loop may take at most 2/3 of the 0xFF context's
  wall time, leaving >=1/3 for BTstack HCI/L2CAP, which is what actually moves
  our bytes. SBC steady state is 375 x 574 = **21.5%**, far below. Derived from
  `elapsed_us`, the current tick's own measured interval, never from
  `PL_A2DP_AUDIO_TIMEOUT_MS` (`a2dp.c:77`: "NO DERIVATION IN THIS FILE MAY
  ASSUME 100 ticks/s").
- **Backstop, 6000 us** — derivation, previously absent: *one tick's fill must
  not overrun the next tick's deadline*. Nominal media period is 10 ms and the
  real one ~11.3 ms, so a cap at ~55% of the nominal period leaves >=4 ms of
  slack even if the run loop fires early. That is what 6000 is.

**Verdict: worst-case dwell is 6.0 ms (unchanged constant, newly reachable),
and typical dwell is unchanged for SBC.** SBC's work bound is
`2 x 4.24 x 800 = 6784 us`, above the backstop, so SBC's operative bound is
still 6000 — **this design does not change the numeric bound on the one code
path currently proven audible.** What changes is that the loop can reach it.
Safety rests on four legs:

1. **USB is protected by priority, not by dwell** — the 0xC0 worker preempts
   the 0xFF media IRQ (`usb_pump.c:21-23`). *Falsifier, pre-existing:*
   `pl_usb_pump_report`'s `worst_interval_us` must stay < 2000 us. If it rises
   after this ships, the preemption model is wrong and this is reverted.
2. **The media watchdog is kicked at tick entry** (`a2dp.c:563`), before the
   fill loop, so a long dwell is not mistaken for a stalled timer.
3. **The backstop is below the tick period**, so a tick cannot eat its
   successor.
4. **Grant delivery is not starved**, by the duty bound. *Needs-measurement*:
   the one leg with no prior evidence — items (g) and (h).

**Consequence for LDAC.** The `2026-08-30-ldac.md` stopping rule of
~1400 us/frame is 1400 x 375 = **52.5% duty**, inside a 2/3 budget with only
1.27x catch-up headroom — not enough to absorb a stall. At **1100 us/frame**
duty is 41% and headroom is 1.6x, matching SBC's margin. **The stopping rule is
amended to ~1100 us/frame** so L0's benchmark measures against a bar this drain
can honour. This makes core1 *more* likely, which is the honest direction.

### D5 — Where this meets `pico-link-cz0.5.6` (vtable uniformisation)

`cz0.5.6` is sequenced **after** this bead. Two lines encode the fixed-frame
assumption and this design removes both, so cz0.5.6 becomes a change to
`codec_sbc.c` and `codec_table.h` only, with **no further drain edit**:

- **`a2dp.c:537`, `num_frames = bytes_in_storage / frame_bytes`.** Gone.
  `frames` is accumulated during fill, one increment per successful `encode()`,
  and stored at seal. A variable-length codec needs no different treatment.
- **`a2dp.c:470` / `a2dp.c:686`, the packet-full predicate.** Collapses to one
  private helper `payload_full(head)` with exactly one call site; the
  timer-handler duplicate at `:686` disappears, since sealing now happens
  inside the loop. Today it reads `encoded_frame_bytes`; after cz0.5.6 it reads
  the encode-out struct's `payload_complete`. **One line, one place.**

Explicit meeting point, to be written into cz0.5.6's spec: slot **byte 0 is a
reserved media-payload header**, owned by `a2dp.c` today and by the *codec*
after cz0.5.6. cz0.5.6 adds `uint8_t header_bytes` to `pl_codec_frame_info_t`
so the offset stops being a hardcoded `1`. **Do not hardcode `1` in any new
code this bead adds** — route it through `pl_a2dp_usable_payload`, which
already exists as the single correction point (`a2dp.c:385-401`).

### D6 — Lifecycle: SUSPEND, stop, reconnect

A stale payload surviving into a new stream is an audible artefact — a burst of
the *previous* track with an RTP timestamp from the previous timeline. Flush
the queue at every point that today calls `pl_pcm_reset()`, and at one more:

| Site | Action |
|---|---|
| `STREAM_ESTABLISHED` (`a2dp.c:842`) | reset head/tail/count/send_requested; `rtp_next = 0` |
| `STREAM_SUSPENDED` (`:1015`) | same, **except `rtp_next` is preserved** — auto-resume continues one timeline |
| `STREAM_RELEASED` (`:1028`) | same as ESTABLISHED |
| `SIGNALING_CONNECTION_RELEASED` (`:1041`) | same as ESTABLISHED — **this handler flushes nothing today, not even the PCM ring**; add both |

**A grant can arrive after a flush.** `send_requested` may already be true
inside BTstack, so `CAN_SEND_MEDIA_PACKET_NOW` still fires once. The new send
path's first line handles it.

**This is a real bug today**, found while reading for this design and
independently confirmed by the orchestrator: `pl_a2dp_send_media_packet`
(`a2dp.c:534-552`) checks neither state nor `sbc_storage_count`. After SUSPEND
clears the buffer at `:1018-1019`, a pending grant still transmits a 1-byte
payload with `num_frames = 0`. Harmless in practice (a sink discards it) but it
is an unsolicited malformed packet on a live AVDTP stream, and it stops being
harmless against a strict sink. Fixed as a side effect of D1.

### D7 — Counters (all `volatile uint32_t`, read only by `pl_a2dp_report`)

Added:
- `payloads_sealed` — its rate vs `pkt_sent`'s rate is the single most
  important new signal; divergence means the send side is the limiter.
- `stop_queue_full` — **the new ceiling tripwire**, inheriting
  `stop_packet_full_hot`'s job.
- `tx_depth_max` — high-water of `tx_count`, **reset at STREAM_STARTED**
  (per r44: high-water marks that never reset poison later derivations).
- `grants` — `CAN_SEND_MEDIA_PACKET_NOW` events; `grants/s` vs `pkt_sent/s`
  separates "grants are slow" from "we did not ask".
- `spurious_grants` — grant with an empty queue (D6).
- `dwell_max_us` — high-water of fill dwell, reset at STREAM_STARTED. Without
  it, "`stop_dwell` is 0" says nothing about how close the budget came.

Retired: `stop_packet_full_hot` (its ceiling is what this bead removes),
`ticks_send_pending` (no `sbc_ready_to_send` left to pend on), `stop_packet_full`
(no longer a stop reason; `payloads_sealed` counts the same event correctly).

## Alternatives considered

1. **"Send N packets per tick."** Rejected — the rescoping's whole point: keeps
   fill and send coupled, needs its own magic N, and leaves the "tick with a
   pending send does no filling" defect intact.
2. **Also fill from the `CAN_SEND_NOW` handler.** Rejected: puts encode dwell
   inside the send path (what D4 budgets against), creates a second producer
   for state otherwise proven single-producer, and buys nothing — the credit
   clock is tick-driven, so there is no extra credit to spend at grant time.
3. **One large contiguous buffer with byte offsets.** Same RAM, saves nothing,
   reintroduces a partial-packet wrap case in IRQ context.
4. **Depth 2 (double-buffer).** Smallest change that fixes the defect.
   Rejected: at `B_tick = 2` it fills within a single tick, degenerating into
   today's behaviour under exactly the catch-up bursts it exists to absorb —
   and it fails LDAC HQ, the reason this bead exists.
5. **Grow the dwell budget** instead of a queue. Does not help: the limiter is
   payload room, not time.
6. **Shorten the media tick to 5 ms.** Already rejected in
   `2026-08-30-ldac.md`: doubles IRQ load and relies on pico-sdk truncation
   behaviour `a2dp.c:76-85` forbids depending on.

## Consequences

- The one-packet-per-tick ceiling is removed; the drain becomes bounded by ACL
  credits and by the dwell budget, both measurable.
- **The catch-up burst becomes real for the first time.** The nzw clamp permits
  `samples_owed` up to `ring_fill/4 + 128` — with a full ring that is
  8192 + 128 sample-frames, about **170 ms of audio** the drain may deliver
  ahead of real time once it can actually retire it. Sink jitter buffers are
  typically 100-200 ms. **Needs-measurement, and a live risk**: if a sink
  stutters after a stall, the remedy is to tighten the nzw clamp to a fixed
  ~100 ms of catch-up (4800 sample-frames), **not** to reintroduce a per-tick
  cap. Do not pre-emptively change nzw — it is unmeasured on hardware too.
- `pico-link-baj` is **closed by D4**, not deferred. No second underived
  constant is introduced.
- `2026-08-30-ldac.md`'s stopping rule tightens from ~1400 to ~1100 us/frame.
  Its L1 acceptance criterion must be restated against `stop_queue_full`.
- `2026-08-29-a2dp-source-pipeline.md` sec 5's send-path description is
  superseded by D1.
- +4.2 kB `.bss`. One latent bug fixed incidentally (D6).

## Acceptance (for the implementing bead)

1. `stop_queue_full` reads **0** while SBC streams 60 s. Nonzero means the send
   side is the limiter — read `grants/s`.
2. `payloads_sealed` rate == `pkt_sent` rate within 1/s over 60 s.
3. `enc_frames_total` rate still **375 +/-2 /s** — the credit pacer is
   untouched and must prove it.
4. `stop_dwell` reads 0 **and** `dwell_max_us` is reported. A zero `stop_dwell`
   with an unreported high-water is not evidence.
5. `pl_usb_pump_report`'s `worst_interval_us` stays **< 2000 us**.
6. **SBC still audible on real headphones.** This edits the only path proven
   audible; a green counter sheet is not the acceptance criterion.
7. Synthetic overload: a `PL_DEBUG_*`-gated x3 credit accrual must sustain >=3x
   today's packet rate with `stop_queue_full == 0` — that is what proves the
   ceiling is gone rather than merely not binding at SBC's rate.
